# Trident — מנוע החתיכות

**השאלה שהמסמך עונה עליה:** איך ImageSrv שולח אימג' לעשרות מחשבים בשידור אחד,
בלי שמקלט איטי יאט את כולם, ואיך הוא יודע שמה שנכתב לדיסק הוא בדיוק מה שהיה באימג'.

המנוע הוא הבינארי `agent/chunkcast.c` (שולח ומקלט באותו קובץ). הפרוטוקול נקרא
Trident. כל הפניה כאן היא `קובץ:סימבול`, כדי שאפשר יהיה לבדוק כל טענה מול הקוד.
שדות ה-API והמניפסט מוגדרים ב-[interfaces.md](interfaces.md), והוא מקור האמת להם.
כאן הם מוזכרים בשמם בלבד.

## 1. למה הוא קיים

הכלי הקודם (udpcast) שלח פרוסה וחיכה שכל מקלט יאשר אותה, ורק אז המשיך. התוצאה:
מקלט איטי האט את החדר, מקלט ששתק נזרק, ומה שכבר עבר אי אפשר היה לבקש שוב
(ההערה בראש `agent/chunkcast.c`). udpcast הוסר, ו-Trident הוא מנוע השידור היחיד
(`server/rounds/chunksend.py:engine_of` מחזיר תמיד `chunk`).

| | udpcast (הוסר) | Trident |
|---|---|---|
| המתנה לאישור | השולח מחכה לכל המקלטים אחרי כל פרוסה | השולח אינו מחכה לאיש. מעבר אחד על כל החתיכות |
| מקלט איטי | מאט את כולם | מפספס חתיכות ומשלים אותן אחר כך |
| מה שחסר | אי אפשר לבקש | "מה חסר" הוא מה שאינו ביומן העמידות של השרת, ואין הודעת בקשה ב-UDP |
| קצב | קצב אחד | שני קצבים: מה שעל הכבל, ומה שהדיסקים צריכים לכתוב |

**שני הקצבים** (`agent/chunkcast.c`, ההערה "The sender holds TWO rates"):
`--kbps` הוא הבתים הדחוסים שעל הכבל, ו-`--write-kbps` הוא הבתים הפרוסים שהדיסקים
נדרשים לכתוב. האיטי מביניהם קובע. הסיבה: חתיכה של אפסים דחוסה לחבילה אחת בערך,
ואז הכבל "רץ" קדימה בלי שאף דיסק יכול ללכת אחריו. השרת מעביר את שניהם לשולח ב-`server/rounds/chunksend.py:ChunkEngine._command`,
והחישוב שלהם ב-`_start_rate` וב-`_write_kbps`.

## 2. התמונה הכללית

```
Cloner (agent + chunkcast recv)    Server API                 Server (chunkcast send)
        |                              |                                |
 1      |-- chunk-pass: listening ---->|                                |
        |<-- receive, pass=1 ----------|   (after every member listens) |
 2      |                              |------- start pass 1 ---------->|
        |<========= ANNOUNCE x3 (multicast 239.84.82.1:7713) ==========|
 3      |<========= DATA, DATA, DATA ... chunk after chunk ============|  no ACK
        |-- TRF1 feedback (UDP :7714, every 100 ms) ------------------->|  rate +2% / -20%
        |   verify (zstd, XXH64, BLAKE3) -> write -> fdatasync          |
        |<========= END x4 ============================================|
 4      |-- chunk-pass: ended, durable ranges -->|                      |
        |                              | repair.plan: what is missing   |
 5      |<-- receive, pass=2 ----------|  missing on 2+ machines: multicast repair pass
        |<-- fetch, ranges ------------|  missing on one machine: HTTP Range
        |-- GET /api/v1/images/<id>/files/<name>, Range: bytes=A-B ---->|
        |<-- done ---------------------|                                |
```

הקבוצה והפורטים: `server/core/ports.py` (`TRIDENT_GROUP`, `TRIDENT_DATA` = 7713,
`TRIDENT_CONTROL` = 7714). בפועל הנתונים הם `portbase + 2` והמשוב `portbase + 3`
(`server/rounds/chunksend.py:PORT_OFFSET`). המשוב הוא unicast לכתובת השולח, ולא
נשלח לקבוצה.

## 3. היחידות: session, chunk, pass

**chunk (חתיכה)**: 4 MiB מזרם הנתונים של המחיצה (`agent/chunkcast.c:CC_CHUNK`).
כל חתיכה דחוסה לבדה ב-zstd, ולכן אפשר לבקש, לבדוק ולכתוב כל אחת בנפרד. האורך
והגיבוב שלה נמצאים בשורה שלה באינדקס (`<file>.idx`: היסט, אורך, XXH64). פורמט
האינדקס מוגדר ב-[interfaces.md](interfaces.md), סעיף 7, "אימג' חתיכות".
הקוד שקורא ובודק אותו: `agent/chunkcast.c:cc_index_load`. הקוד שחותך את הזרם:
`agent/chunkcut.c`. רק אימג' בפורמט 2 משודר ב-Trident.
מחיצה מוגבלת ל-2^26 חתיכות (`cc_index_load`, כלומר 256 TiB).

**session**: מספר של 8 בתים בכל חבילה, 16 ספרות hex בשדה `session.chunk.key`.
השרת גוזר אותו מגיבוב של מזהה הגל ושל ערך אקראי לכל עלייה של השרת
(`ChunkEngine.key_for`). הוא **אינו סוד**: הוא מבדיל בין זרמים ואינו מאמת אותם.
מקלט מתעלם מחבילה של session או מחיצה אחרים (`stat_rx.foreign` ב-`cc_recv`).

**pass (מעבר)**: מעבר אחד של השולח על קבוצת חתיכות. מעבר 1 שולח בדרך כלל את כל המחיצה (משכפל שחזר באמצע גל ואימת מה שכבר כתב,
`ChunkEngine._first_pass`, מקבל רק את החסר).
מעבר השלמה שולח רק רשימה (`--chunks-file`, בקובץ ולא בארגומנט, כי חוסר מפוזר
הוא אלפי טווחים). מספר המעבר נמצא ב-ANNOUNCE וב-END, ובשדה `pass` של
`POST /api/v1/agent/chunk-pass`. בצד השרת: `ChunkEngine._send`.

## 4. מבנה החבילות

הכול big-endian, UDP. הגדרות: `agent/chunkcast.c` (`CC_MAGIC`, `CC_VERSION`,
`CC_HDR`, `CC_DATA_HDR`) ו-`agent/chunkcast_fec.h:CC_PAYLOAD`.

כותרת של 16 בתים בכל חבילה (`cc_head`):

| בתים | שדה |
|---|---|
| 0-3 | קסם `ISC1` |
| 4 | סוג החבילה |
| 5 | גרסת פרוטוקול (היום 1). חבילה של גרסה אחרת אינה נלקחת, והמקלט אומר זאת בשמה |
| 6-7 | אינדקס המחיצה |
| 8-15 | session |

| סוג | שם | גוף | מתי |
|---|---|---|---|
| 1 | ANNOUNCE | מעבר (4), מספר החתיכות (8), XXH64 של האינדקס (8) | לפני הנתונים, ופעם בשנייה (`cc_keepalive`) |
| 2 | DATA | חתיכה (8), אורך הפריים הדחוס (4), מספר חבילה בחתיכה (4), עד 1,440 בתים של הפריים | חבילה אחרי חבילה |
| 3 | END | מעבר (4), כמה חתיכות נשלחו (8), XXH64 של האינדקס (8) | בסוף המעבר, כמה פעמים (למטה) |
| 4 | PARITY | כמו DATA, ובמקום מספר חבילה: מספר הקבוצה. 1,440 בתים של XOR | רק עם `--fec` (סעיף 8) |

השרת מפעיל את השולח עם `--lead-ms 400 --tail-ms 300`, כלומר 3 שליחות ANNOUNCE לפני
הנתונים ו-4 שליחות END אחריהם (`chunksend.py:DEFAULT_LEAD_MS`, `DEFAULT_TAIL_MS`).
ברירות המחדל של הבינארי עצמו גדולות יותר (`cc_say`).

חבילה שלמה היא לכל היותר 16 + 16 + 1,440 = 1,472 בתים (`CC_PKT`), כלומר 1,500
עם כותרות IP ו-UDP. זה חישוב מהקבועים. לא נמדד על רשת.

מקלט מתעלם מחבילת DATA שאורך הפריים שלה אינו האורך שבאינדקס, או שמספר החבילה
או אורך הגוף שלה אינם אפשריים לחתיכה הזו (`cc_data`, ספירה ב-`stat_rx.bad_pkt`).
ANNOUNCE שסותר את האינדקס שבידי המקלט נרשם ומתעלמים ממנו, ואינו עוצר את המקלט.
אם אף חתיכה מהזרם הזה לא תאמה, המקלט יוצא ב-7.

**אין חבילת בקשה.** המקלט לעולם אינו מבקש חבילה ב-UDP.
ההשלמה היא בבקרה מול השרת (סעיף 6).

## 5. משוב הקצב

השולח אינו מחכה לאישורים, אבל כן שומע על עומס. כל מקלט שולח לשולח דיווח של
56 בתים (`TRF1`) לכל היותר פעם ב-100 מ"ש (`cc_recv` קורא ל-`cc_feedback_report`).
כתובת השולח נלמדת מ-ANNOUNCE של אותו מעבר ואותו אינדקס. מבנה הדיווח מופיע
ב-[interfaces.md](interfaces.md), "Trident in-wave rate feedback". שלושה מספרים
בו מניעים את ההחלטה:

- `written`: כמה חתיכות נכתבו, המינימום מכל הדיסקים החיים של המחשב;
- `backlog`: כמה בתים ממתינים לכתיבה או נכתבים עכשיו, ועוד מה שממתין לאימות;
- `drops`: מונה **מצטבר** של חתיכות שהמקלט נאלץ לוותר עליהן. מצטבר, כדי שדיווח
  שאבד ברשת לא יסתיר אותן.

השולח מחליט כל 100 מ"ש (`cc_feedback_tick`):

| מצב | פעולה |
|---|---|
| כל המקלטים עם backlog מתחת ל-8 MiB ובלי עלייה ב-`drops` | הקצב עולה ב-2% מקצב ההתחלה (`increase`) |
| מקלט עם backlog מעל 24 MiB, או עלייה ב-`drops` | הקצב יורד ל-80% (`decrease`) |
| דיווח ישן מ-300 מ"ש (`CC_FB_FRESH_MS`) | אינו מאשר עלייה (`missing`) |
| מקלט שותק 2 שניות | אינו נספר |
| מקלט שעבר את הסף 10 החלטות ברצף בזמן שהאחרים בריאים | נרשם `left-behind`, ואינו מכריע יותר |

הקצב תמיד בין `--rate-min` ל-`--rate-max`. עם `--rate-cap`, התקרה עצמה יכולה
לגדול ב-10% אחרי 20 החלטות רצופות על התקרה בלי מקלט בעייתי (`CC_FB_WIDEN_TICKS`),
ויורדת חזרה בהחלטת `decrease` הראשונה.
ההחלטות עצמן (הגבולות, `--rate-cap`) מגיעות מהמוח בשרת:
`server/rounds/chunksend.py:feedback_bounds`.
כל החלטה מודפסת (`rate <kbps> <reason>`), ולכן אפשר לשחזר אותה מהיומן.

**המשוב הוא ייעוץ בלבד.** הוא אינו מתיר כתיבה ואינו מוכיח עמידות (`cc_feedback_report`:
"completion is write completion, NOT durability"). בלי אף דיווח השולח נשאר בקצב ההתחלה.

## 6. תיקון חסרים

אחרי מעבר 1 כל מחשב מדווח לשרת אילו חתיכות **עמידות** אצלו (`durable`, טווחים
סגורים). "מה חסר" הוא המשלים של זה. ההכרעה: `server/rounds/repair.py:plan`.

| מה חסר | מי ממלא | איפה בקוד |
|---|---|---|
| חתיכה ל-2 מחשבים או יותר (`repairrule.MULTICAST_MIN`) | מעבר השלמה במולטיקאסט, `chunkcast send --chunks-file` | `repair.plan` (`Plan.multicast`) |
| חתיכה למחשב אחד | המחשב מוריד אותה ב-HTTP, בקשת `Range` לקובץ המחיצה | `agent/lib/restore/chunkfetch.sh:_chunk_fetch`, `server/agent/api.py:image_file` |
| דיסק שעדיין חסר אחרי 5 סבבים (`MAX_ROUNDS`) | לא ממלא: הדיסק נכשל בשמו | `repair.plan` (`Plan.failed`), `server/brain/repairrule.py` |

בהפצה ישירה (מחשב הבנייה משדר מהדיסק שלו) אין קובץ בשרת להוריד ממנו, ולכן הסף הוא 1
וכל חוסר חוזר במולטיקאסט (`repairrule.threshold`).
מחשב מקבל פעולה אחת בכל סבב. מה שחסר רק לו ממתין לסבב שאחרי מעבר ההשלמה.

**HTTP Range.** `curl` אחד עם בקשת `Range` לכל טווח על חיבור אחד, ו-`chunkcast apply`
אחד שקורא את הפריימים מ-stdin לפי הסדר. אותו שער אימות כמו במקלט (סעיף 7).
`apply` יוצא ב-8 אם פריים שהגיע קצר או לא תואם (`cc_apply`).

**דיסק איטי אינו כישלון.** חתיכה שהחוצץ של מגירה איטית לא הספיק לקבל נספרת
(`skipped`) ומושלמת כמו כל חוסר (`repair.slow_reason`). כישלון נשאר רק לכתיבה
שנכשלה, או למגירה שלא החזירה כתיבה במשך `CC_WRITE_STALL_MS` (120 שניות).

**מחשב שכן (P2P).** מחשב משכפל שכבר יש לו את החתיכה יכול להגיש אותה למחשב אחר באותו
גל: `chunkcast serve` מגיש `Range` של פריימים שלמים, עם אסימון לכל שיבוץ
(`sv_token_ok`, השוואה בזמן קבוע) ו-`--allow` לכתובת אחת. בצד המקבל `chunkcast apply`
מאמת כמו תמיד. **ברירת המחדל היא מצב צל** (`brain_peer_mode`): השרת רושם מה היה
מחליט, והביצוע נשאר ב-HTTP מהשרת. פרטים: [interfaces.md](interfaces.md), "השלמה
ממשכפל שכן". בלי רשימת BLAKE3 אין P2P בכלל.

**HTTP במקביל לזרם** (`fetch_parallel`, כבוי כברירת מחדל): חתיכות יורדות ב-HTTP בזמן
שהזרם רץ, דרך FIFO, לאותם כותבים (`agent/chunkcast.c:cc_feeder`).

## 7. אימות, וכתיבה רק אחרי אימות

חתיכה מגיעה לדיסק בדרך אחת, ב-`recv` וב-`apply` כאחד (ההערה "A chunk reaches a
disk only this way"):

```
packets -> assembly slot (4) -> verifier queue -> cc_verify -> writer queue -> cc_write -> fdatasync -> state file
 cc_data                         cc_hand        zstd, length,   cc_writer      cc_walk     cc_sync     cc_state_write
                                                XXH64, BLAKE3
```

1. **הרכבה.** חבילות של חתיכה נאספות באחת מ-4 משבצות (`CC_SLOTS`, `cc_data`).
   חתיכה שלא הושלמה והמשבצת שלה נדרשת נזרקת וחסרה (`evicted`). חתיכה שלמה
   שהתור מלא ממתינה במשבצת (`deferred`) ונספרת ב-`backlog` של המשוב.
2. **אימות** (`cc_verify`, ב-threads של `cc_verifier`): הפריים נפרס, האורך שווה לאורך
   החתיכה, ה-XXH64 של התוכן הפרוס שווה לאינדקס, וה-BLAKE3 שלו שווה לרשימה.
   חתיכה שנכשלה **אינה נכתבת** ונשארת חסרה. הסיבה נרשמת (`bad_chunk k`).
3. **כתיבה** למקומה: דרך מפת הסיביות של partclone, או בהיסט `k × 4 MiB` במחיצה
   גולמית (`cc_write`, `cc_walk`). יעד חייב להיות התקן בלוק (`cc_open`; קובץ רגיל מותר רק בבדיקות).
4. **flush.** `fdatasync` בתהליכון משלו (`cc_flusher`, `cc_sync`). רק חתיכה
   שנכתבה **לפני שה-flush התחיל**, וה-flush הצליח, נעשית עמידה. flush שנכשל מכשיל
   את היעד בשמו ואינו מוסיף דבר.
5. **קובץ המצב** (`cc_state_write`, בזיכרון של הסוכן, לא על דיסק יעד) הוא מה שמדווח
   לשרת כ-`durable`.

**למה שני גיבובים.** XXH64 מוצא חתיכה פגומה, ואינו עוצר חתיכה שנבנתה בכוונה: הוא
אינו קריפטוגרפי, ואפשר לבנות בלוק עם תוכן לבחירה ו-XXH64 נתון (ההערה בראש
`agent/chunkcast.c`). לכן לכל מחיצה יש גם רשימת BLAKE3 של 32 בתים לחתיכה,
והמניפסט נושא את ה-BLAKE3 של הרשימה עצמה (`chunk_b3`). ה-XXH64 של האינדקס נמצא
ב-`index_xxh64`. שתי הרשימות נבדקות מול המניפסט לפני שמאמינים לאחת
מהשורות (`cc_index_load`, `cc_b3_load`). הסוכן אינו כותב בלי הרשימה: מניפסט בלעדיה, או
רשימה שלא ירדה, מכשילים את המגירות בשמן (`agent/lib/restore/chunkb3.sh:chunk_b3_fetch`).
ללא `--b3-file` הבינארי בודק XXH64 בלבד ואומר זאת פעם אחת (`cc_b3_setup`),
וזה נועד לבדיקות.

מה שהמנוע **אינו** עושה: קריאה חוזרת מהדיסק אחרי הכתיבה. היא שלב נפרד של הסוכן
(`readback.sh`, במדגם או במלואה), שרץ גם במסלול הזה.

## 8. תיקון חבילות (FEC), אופציונלי

עם `--fec` בשולח, אחרי כל 32 חבילות DATA של פריים (`FEC_K`) נשלחת חבילה אחת מסוג
PARITY: XOR של 1,440 בתים (`agent/chunkcast_fec.h:fec_encode`). מקלט שחסרה לו חבילה
אחת בלבד בקבוצה משחזר אותה (`fec_decode`, נקרא מ-`cc_data`). קבוצה שחסרות בה שתיים
או יותר אינה משוחזרת, והחתיכה מושלמת כמו תמיד. מה ששוחזר עובר את אותו אימות מלא.
המקלט דורש `--fec` ורשימת BLAKE3 (`cc_recv`, יציאה 2 בלעדיהם). אין משא ומתן בין
הצדדים. בקוד השרת והסוכן **אין מקום שמעביר `--fec`**: היכולת קיימת בבינארי
ובבדיקות, והשרת רק אוסף ראיות על אבדן חבילות (`server/brain/fecrule.py`).

## 9. גבולות אמון

| מה | על מה נשען |
|---|---|
| המניפסט, האינדקס ורשימת BLAKE3 | מגיעים בערוץ ה-HTTPS של הסוכן (7712). המקלט מאמין להם רק אחרי שהגיבוב שלהם שווה לערך במניפסט. אמון המניפסט נשען על ה-CA ב-initrd, כמתואר ב-[security-model.md](security-model.md) |
| תוכן החתיכות | **אינו נשען על הרשת.** כל חתיכה נבדקת מול הרשימות. חבילה מזויפת אינה יכולה לגרום לכתיבת תוכן אחר |
| מקור החבילות | `--from` מסנן לפי כתובת המקור של השרת (`session.chunk.source`). חבילה מכתובת אחרת נזרקת ונספרת (`stray`). כתובת מקור אינה חתימה: מה שעוצר זיוף הוא הוילן והסוויץ' |
| משוב הקצב | לא מאומת. מי שמגיע לפורט 7714 יכול להוריד את הקצב. הוא אינו יכול לגרום לכתיבה. מוגבל ל-1,024 זהויות (`CC_FB_PEERS`), ודיווח לא תקין נספר (`malformed`) |
| מולטיקאסט | לא מוצפן ולא חתום. מבודד ברשת ההפצה. חומת האש פותחת את 7713-7714 רק למחשבים רשומים (`deploy/nftables-rules.sh`) |
| שרת שכן | TCP בלי TLS. מוגן באסימון (נקרא מקובץ ולא מארגומנט), `--allow`, ו-`--until-s` לסיום עצמי. פריימים שמגיעים ממנו נבדקים כמו כל פריים |

הפער הידוע: מי ששולט ברשת ההפצה יכול להפריע (להוריד קצב, להציף חבילות, לגרום
להשלמות מיותרות), אך לא לשנות מה שנכתב. ראו גם את הפערים הרחבים יותר ב-[security-model.md](security-model.md).

## 10. מגבלות ידועות

- **IPv4 בלבד.** כתובות מנותחות כ-`AF_INET` (`cc_addr`).
- **גילוי אבדן רק בסוף מעבר.** אין NACK ב-UDP, ולכן חוסר מתגלה כשהמקלט מדווח
  `ended` ומקבל תוכנית השלמה. בחתיכה שחבילה חסרה בה, ובלי `--fec`, כל החתיכה
  מושלמת.
- **מקלט בלי משוב.** בלי דיווח אחד לאורך המעבר, השולח נשאר בקצב ההתחלה.
- **אין קריאה חוזרת בתוך המנוע** (סעיף 7).
- **פורמט 2 בלבד, חתיכה של 4 MiB קבועה.** הפורמט הישן (זרם zstd אחד) אינו
  משודר ב-Trident, וגל על אימג' כזה מסורב לפני הבייט הראשון.
- **גרסת פרוטוקול 1 בלבד.** שרת ואימג' סוכן מגרסאות שונות לא ידברו: המקלט
  אומר "protocol version" ביומן וזורק (`cc_recv`).
- **מגירה תקועה.** כתיבה או flush שלא חזרו 120 שניות מכשילים את המגירה בשמה,
  ושאר המגירות ממשיכות (`CC_WRITE_STALL_MS`, `cc_watch`).
- **קודי יציאה של `recv`:** 0 המעבר נגמר, 3 אין זרם, 4 הזרם השתתק, 5 אין יעד חי,
  6 נעצר באות, 7 אינדקס אחר, 2 שימוש לא נכון (ההערה בראש `agent/chunkcast.c`).
- **אין כאן מספרי ביצועים**, בכוונה: מספר בלי סביבה ומקור הוא ציטוט ולא ראיה.
